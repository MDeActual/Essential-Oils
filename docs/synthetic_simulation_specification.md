# synthetic_simulation_specification.md — Synthetic Simulation Specification

## Purpose

This document specifies the Synthetic Simulation Environment for the Phyto.ai platform: the system that generates synthetic user profiles and contributor records for protocol validation, development testing, and pre-deployment adherence curve prediction.

Simulation data must be strictly isolated from production analytics. Mixing synthetic data with real contributor data is a critical data integrity violation (LOCK-003).

---

## Governing Rules

- **LOCK-003**: Synthetic simulation data must never be mixed into production analytics without explicit isolation flags.
- **LOCK-004**: The Simulation Agent (as defined in `AGENTS.md`) operates in an isolated simulation context only. It has MEDIUM authority within that context; it has no authority over production data.
- **Analytics integrity**: Only `real_contributor` records are analytics-eligible. Synthetic records are permanently excluded from scoring.

---

## Simulation Architecture

```
Protocol Spec + Synthetic User Profiles
        ↓
Simulation Agent (isolated context)
        ↓
generateSyntheticContributorRecord() / generateSyntheticContributorBatch()
        ↓
Records tagged: data_origin: "synthetic_simulation", isolation_flag: true
        ↓
Simulation Validation (assertSyntheticIsolation, assertBatchIsolation)
        ↓
Simulation Run Report (predicted adherence curves, validation results)
```

## Core Types

Defined in `src/simulation/types.ts`:

### DataOrigin Enum

```typescript
enum DataOrigin {
  RealContributor = "real_contributor",
  SyntheticSimulation = "synthetic_simulation",
}
```

All synthetic records must use `DataOrigin.SyntheticSimulation`. This value is immutable after record creation.

### ExclusionStatus Enum

```typescript
enum ExclusionStatus {
  Included = "included",
  Excluded = "excluded",
}
```

All synthetic records must have `ExclusionStatus.Excluded` to prevent analytics pipeline eligibility.

### SimulationContext

A `SimulationContext` groups all records belonging to a single simulation run. It carries the isolation metadata required for downstream validation.

Key fields:
- `simulationId` — unique identifier for the run
- `protocolId` — the protocol being simulated
- `runAt` — ISO 8601 timestamp
- `isolation_flag: true` — mandatory; asserted by `assertSyntheticIsolation()`

### SimulationBatch

A collection of `SyntheticContributorRecord` objects belonging to a single `SimulationContext`. Used for batch validation and report generation.

## Generation Rules

### Rule SIM-001: Mandatory Isolation Flag

Every synthetic record generated by `generateSyntheticContributorRecord()` must have:

```json
{
  "data_origin": "synthetic_simulation",
  "exclusion_status": "excluded",
  "isolation_flag": true
}
```

Enforcement: `generateSyntheticContributorRecord()` in `src/simulation/generators.ts` sets these fields unconditionally. They cannot be overridden by callers.

### Rule SIM-002: No Real User Data in Simulations

Synthetic user profiles must be generated from `SyntheticRecordOptions` specifications — never by copying or deriving from real `User Profile` entities. Simulation data must not contain real `userId` values.

### Rule SIM-003: Adherence Range

Synthetic records may model any adherence score in the range [0, 100]. The simulation layer does not apply the 50% analytics eligibility threshold — that threshold applies only to production analytics. Within simulation, records of all adherence levels are valid for testing purposes.

### Rule SIM-004: Batch Size Limits

| Context | Maximum batch size |
|---------|-------------------|
| Development / unit test | 1,000 records |
| Protocol validation run | 10,000 records |
| Population-level simulation | 100,000 records (requires explicit human approval flag) |

### Rule SIM-005: Simulation Data Must Not Be Persisted to Production Database

Simulation records must be stored only in:
- In-memory simulation context during a run
- A clearly labeled simulation database or test database
- Exported simulation report files

They must **never** be inserted into the production `Contributor` table or any analytics-eligible data store.

## Validation Functions

Defined in `src/simulation/validation.ts`:

| Function | Purpose |
|----------|---------|
| `validateContributorRecord(record)` | Validates a single record's required fields and data integrity constraints |
| `validateContributorRecordCollection(records)` | Validates a batch of records; returns per-record error set |
| `assertSyntheticIsolation(record)` | Throws if `data_origin` is not `synthetic_simulation` or `isolation_flag` is not `true` |
| `assertBatchIsolation(batch)` | Asserts all records in a batch are isolated; throws on any real-contributor record |
| `filterAnalyticsEligible(records)` | Filters to only `real_contributor` records with `adherence_score ≥ 50`; returns empty array for a pure synthetic batch |

**Rule SIM-006**: `assertBatchIsolation()` must be called before any simulation batch is passed to the analytics pipeline, even in test environments.

## Simulation Run Report

Each simulation run must produce a `SimulationRunReport`:

```json
{
  "report_id": "sim-YYYY-MM-DD-NNN",
  "simulation_id": "...",
  "protocol_id": "...",
  "protocol_version": "MAJOR.MINOR.PATCH",
  "run_at": "ISO 8601 timestamp",
  "batch_size": 0,
  "isolation_validated": true,
  "predicted_adherence_curve": {
    "mean_adherence": 0.0,
    "p25_adherence": 0.0,
    "p50_adherence": 0.0,
    "p75_adherence": 0.0,
    "phase_drop_off_points": []
  },
  "validation_result": "pass | fail",
  "validation_errors": []
}
```

Reports are used by the Protocol Evolution System as pre-deployment validation evidence before promoting a protocol amendment to `active` status.

## Use Cases

### 1. Protocol Validation Before Launch

Before a new protocol version is promoted from `draft` to `active`:
1. The Simulation Agent generates a batch of synthetic contributor records matching the target user demographic profile.
2. The simulation runs against the protocol and produces a `SimulationRunReport`.
3. If `predicted_adherence_curve.mean_adherence` is below a threshold (configurable per protocol, default 0.55), the protocol is flagged for revision.
4. The report is attached to the Protocol Amendment ADR entry.

### 2. Regression Testing for Protocol Amendments

When a protocol amendment (MINOR or MAJOR version bump) is proposed:
1. Run the simulation against both the current version and the proposed amended version.
2. Compare `predicted_adherence_curve` results.
3. If the amended version predicts lower adherence than the current version, a `regression_alert` signal is generated and the amendment is blocked pending human review.

### 3. Development and Unit Testing

Simulation generators are used in unit tests to produce realistic contributor record fixtures without touching production data. All test-generated records automatically carry `data_origin: synthetic_simulation` per SIM-001.
